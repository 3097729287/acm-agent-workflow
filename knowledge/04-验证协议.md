# 验证协议：先钉基准，禁止同源互拍

> 类型：方法 ｜ 给一个结论做验证时的固定顺序、高发错误与机制

给一个结论做验证时，**最大的风险是"验证工具本身写错"，而不是被验证的对象写错**。
本协议分三部分：算法结论怎么验、验证工具自己怎么验、改文件怎么不写坏。

## 核心原则

**先钉死一部可信基准，只与它比对；禁止拿"自己另写的实现"当标尺。**

原因：同一份理解写出的两份实现，**错误会同源**。两个都错、却互相"验证通过"，比不验证更糟——
因为它给出的是虚假的确定感。实例：`判据版`（贪心 DP）和 `图写法`（双重排列枚举）
同时验证"通过"，实际是两份判据方向都反了。

## 固定顺序（照做）

1. **只写一份"基准实现"**，优先在另一种语言里按最直白的规则写（Python 极小极大 / 直接枚举），
   并在**固定小样例**上逐个中间量手算核对。基准没被手算校对过之前，不进入下一步。
2. **互拍必须不同实现范式**（递归 vs 迭代、位掩码 vs 集合、匹配 vs 枚举），
   且每份独立对着**手算过的期望值**校一遍，再进入随机互拍。
3. **先手算 2~3 个能一眼看穿的例子，再上随机**。随机数据会掩盖方向性错误
   （布尔取反、上下界、谁先手），小样例才能立刻暴露。
4. **调试时一次只改一处**。同时改"判据方向"和"暴力实现"，错误会互相掩盖，绕圈加倍。
5. **上随机之前先做有界穷举**（$n \le 3$、值域 $\le 8$ 全枚举），它比随机测试更容易抓住边界。
6. **计时报告分开写**：含进程启动的调用耗时 vs 同一进程批量测的纯计算耗时，
   两者可以差一个数量级，混着报会误导（实测 10 ms vs 5 ms）。

## 高发错误模式（写暴力最容易栽的地方）

- **布尔方向弄反**：`gcd == 1` 写成 `gcd > 1`；`Alice 赢` 写成 `Bob 赢`。
- **状态表示不完整**：极大极小只记"双方已出牌集合"，**漏记"对手刚出了哪张"**。
- **算法语义不对**：`cover |= pm` 这种"并集式"转移把同一张牌重复用了，
  而正确语义是"每张只能用一次"（要匹配 / 子集 DP）。
- **记忆化污染**：多组测试共用 memo 表但没按输入重置（尤其 `n` 变化时位宽语义也变）。
- **原地倒序 OR**：新置位的状态在同一轮不传播，应升序或另开数组。

## 验证机制（执行类错误靠机制堵）

### ① 结论不许从没核过的数据里生成

- **脚本实跑一次再信它的输出**：语法检查通过 $\ne$ 逻辑正确。
  反例：测量器函数里用 `Write-Output` 打日志 → 字符串混进返回值 → 报出「冷启动比热启动慢 **485 ms**」这个假数，
  且不报任何错、看起来完全正常（`ParseFile` 语法检查当时返回 OK）。
  做法：函数内打日志一律 `Write-Host`；脚本写完立刻实跑，并检查量级是否合理；负值/空值要显式处理，别静默参与算术。
- **探针先自证观测到了正确对象**：下结论前先让探针**打印一次它认定的目标**（进程 id + 命令行 / 文件路径 / 事件名）。
  反例：测「哪条启动命令更快」时假设了进程树形状——盯的是 `cmd.exe` 的直接子进程，而真正的程序被中间层拉成了
  **孙进程**，量到的是空壳 CPU，得出「B 快 5.5 倍」的假结论。**测不到数据也是信号**（窗口句柄全程空白 = 没观测到目标，不是"结果为零"）。
- **从日志取时间差前，先确认两端事件各由谁产生**（程序 / 用户 / 网络 / 上游）。
  反例：把「会话创建 → 第一条用户消息 = 20.8 秒」当成启动耗时，实际里面混着读界面、打字的时间，
  真正的模型首字延迟只有 1.4 秒。分不清"程序慢"还是"人在操作"的区间，不能当性能指标。
- **报汇总数字前做量级自检**：各项之和 $\approx$ 总数？有无单项大于总数？
  反例：统计一组文件的占比时把无关文件的大小混进了分子，把 48.8% 报成 85.4%。
- **预期从内容推出来，不要先定一个数再让内容去凑**。
  反例：一个"只补两行"的小改动，先凭空预设净增 4 行被拦；改用"按换行分割计数"算出 7 行又错——
  字符串以换行开头时首段是空串，被多算 1 行。先让新内容占固定行数，预期直接取那个数。
- **别人报的验证结论，也要自己实跑一遍再采信**。
  反例（一次外部题解）：对方题解里两处"对拍 N 组全部一致"，把它的脚本原样拿来跑——
  一处第一组就失败、另一处 300 组里失败 190 组；那个 `N` 恰好等于脚本设计的总组数。
  **做法**：引用他人的验证数据前，先跑一遍他的脚本；跑不了就不引用，只写"据其自述"。
- **验证脚本自己会挂死，而且挂得静默**：给子进程喂输入时传错类型（`subprocess` 收到 `str` 而不是 `bytes`），
  写线程抛异常、子进程空等 stdin，脚本一声不响卡到外部超时（实测：卡满 300 秒才被发现）。
  **"没输出"和"挂死"看起来一模一样。** 做法：`subprocess.run(..., timeout=N)` 必须给；
  输入统一 `inp.encode()`（或 `text=True`）；每进一个阶段先打一行，卡住时能看出停在哪一步。

### ② 核对与输入：字符串必须来自原文

一天内 4 次「报某内容丢了、其实没丢」，全是**探测串与原文用词不一致**造成的假阴性：

| 用过的探测串 | 原文实际写法 |
|---|---|
| 文件的完整标题 | 原文用的是简称 / 编号 |
| `写-Host` | `Write-Host` |
| 加粗后的长名 | 原文未加粗 |
| `“无害的形式差异”`（弯引号） | `"无害的形式差异"`（直引号） |

**4 次没有一次是真丢内容。** 根因不是"忘了规则"，而是**取探测串这一步就走了记忆、没走原文**——
基准在生成的那一刻就错了，后面比对再严谨也没用。所以这类问题加规则条文无效（执行类错误，不是决策类），必须改机制：

1. **探测串从文件里取，不从记忆里取。** 要核"某个说法在不在"，先用 `grep` 搜全文的语义近词、把命中的原句打出来再判断；
   禁止凭印象拟一个词去做 `contains`。落地写法：校验项**从刚拼好的变量里截取**，取不到就不校验并出声。
2. **核对输出必须带原文片段（命中位置 + 原句）**，只报"有 / 无"的检查一律不合格——带上原句，口径一歪差异会自己暴露。
3. **"没找到"先当假警报处理。** 假阴性远比假阳性常见；报告"缺失/丢失"前必须先在**全文**里搜语义等价说法。
4. **报"已产出/已存在"之前，先 `grep` 一次确认它真的在。**
   反例：汇报里说「某条规则已并进核对机制那一节」，而该节**从来没写进去过**——插入时锚点失败、方向改了却没回头补，
   后续两轮却一直按"它在"来叙述。**"以为写了" $\ne$ "写了"**。
5. **验证与对拍的输入也必须从原文抄，不凭记忆敲。**
   反例（一次周赛 B 题）：交付前重跑样例，凭记忆手敲输入 `5 10 2 / 1 1 2 2 3`，输出 `10`、
   与题解记录的 `4` 不符——差点去"修"代码；回原始 HTML 一查，真实样例是 `5 6 1 / 1 2 2 4 4`，
   **是输入敲错了**，代码和题解都没问题。
   **危险之处**：它伪装成"代码有 bug"，会让人去改一个本来正确的答案，比没验证更糟。
   做法：样例输入固化成复现脚本里的**常量表**并注明来源，跑之前与原文对一遍。
6. **手推的"期望值"本身也可能是错的：跑出不一致时，先重推期望值，别急着改代码。**
   反例（一次周赛 E 题）：边界用例 `3 / 3 2 1` 手推期望是 `1 2 3`，
   程序输出 `1 1 1` 判为"不通过"。实际第二张 2 与 3 相邻、当场并成一段，**代码是对的、期望值是手推错的**
   （同一份代码的 500 组随机对拍全过、官方样例也过——这两条已经是很强的反证）。
   做法：出现不一致时先把该用例**按题面重新走一遍**，两边都写清楚"为什么是这个数"，
   再决定改哪一边；只有期望值和代码都能自圆其说时才动代码。

**一句话**：核对的产出必须是**原文片段**，不是判断；验证的**输入**同理。

### ③ 「不影响行为」的残留，行为类验证看不见

**反例**：一次性从草稿落盘一个 `.cpp` 时，中间混进了一段**死代码**——一个立刻 `break` 的空 `while`。
它编译通过（`-O2 -std=c++17 -Wall -Wextra` 连警告都没有）、官方样例全过、1539 组对拍全过，
**三道行为类验证没有一道看得见它**；最后是靠"写完后回看整个文件"才发现的。

**为什么**：编译 / 样例 / 对拍验证的都是**程序的行为**。一段不参与执行的残留、一处重复但无害的赋值、一个恒真的条件，
行为上与干净代码**完全等价**，所以这三道关卡在设计上就照不到。**"验证全绿"证明的是行为，不是代码的来源与整洁。**

**做法（祈使句）**：

1. 长代码从草稿一次性落盘后，**编译之前先把整个文件读一遍**（至少读刚写的那几个函数），别把"能过验证"当成"写干净了"；
2. 残留最爱藏在"刚删掉一段逻辑"的位置——删块之后立刻重读该处上下文；
3. 记住验证的**覆盖面**：行为类验证照不到"不影响行为"的代码，格式类验证照不到语义
   （同款结论见《数学 LaTeX》："验证的维度必须包含使用者看到的形态"）。

### ④ 文档里写的调用形式，要按写的那样真跑一遍

**反例 1**：`tools/verify.py` 的 `find_samples()` 只按「workdir 是每题子目录（`<数据根>\题解\<比赛名>\RoundNNN\<区间>\<字母>\`）、`_work` 是它的**兄弟**目录」这一种形态设计。
换成 `--from-md`（workdir 就是场次根，`_work` 是它的**子**目录）时，样例**永远找不到**，直接打印「没找到 samples.py」。
先前测过的是两种**子目录**形态，各自都通——**但那两种恰好共用同一个 `_work` 位置**。

**反例 2**：文档里写过「这几个脚本的用法都是 `python <脚本> --help`」，照这样跑一遍才发现：
有的脚本没做 `--help` 分支，`--help` 被当成路径参数、直接抛 `FileNotFoundError`；
有的则把 `--help` 当选项过滤掉后落进「没给参数」分支、**返回非 0 退出码**（内容打印得完全正确，
但 `python <脚本> --help && echo OK` 这种链会假报失败）——
**文档里承诺的调用形式，自己一次都没那样调过。**

**为什么**：验证覆盖的是「心里想的那条路径」，文档承诺的是「读者会走的那条路径」，两者可以完全不相交。
与《数学 LaTeX》的「验证维度必须包含使用者看到的形态」是同一类病，只是病灶从"渲染"换成了"调用"。

**做法（祈使句）**：

1. 往任何文档里写命令，**照抄那一条真跑一次**；写成 `A && B` 就要确认 A 真返回 0；
2. 一个 helper 收「工作目录」这类参数时，**把流程里实际会用到的每一种形态各跑一遍**
   （每题子目录 / 场次根 / 从别处调用），别只测自己心里想的那一种——**测试用例的多样性要按调用方的实际形态取，不是按顺手的那一种取**；
3. 判定"通了"**要连退出码一起看**：打印了正确内容却返回非 0，在脚本链里等同于失败。

## 结构性改动：重建 + 校验 + 替换，不要用局部编辑

**适用**：给已有文件**增删章节、重排顺序、搬移整块内容**。

**反例（同一天三次）**：
1. 说「把这句挪进索引文件」，实际只从原处删了、新处没加 → 内容凭空消失；
2. 改索引表头「来源：…」那行时把它**替换掉**而非在后追加 → 来源信息丢失；
3. 挪章节顺序时 `old_string`/`new_string` 写反 → **删掉了整节标题**，正文挂到了「相关」下面。

根因不是疏忽，是**用局部替换去做结构调整**：`edit` 只有替换语义，没有插入/移动/删除整块的能力，硬凑必然吃内容。

**做法（祈使句）**：涉及章节增删或重排时，**不要用 `edit` 局部拼**，改走这五步：

1. `read` 原文，拿到真实文本（页码敏感的活别凭记忆做）；
2. 在脚本里拼出**完整的新版本**；
3. 先写**临时文件**（绝不直接改原文件）；
4. 跑**校验清单**——逐条 `contains` 旧章节标题与新内容，任一缺失就中止、保留原文件；
   清单还要覆盖**重复与冗余**：同一片段出现两次同样算失败（`Replace` 的常见副作用）；
5. 校验通过才覆盖原文件（覆盖前把原件按备份规则存进备份仓——`config.json` 的 `backup_root`）。

**位置敏感**：`edit` 锚在末尾追加能保证**不丢内容**，但**不保证位置对**——实测：说好「相关」要收尾，
新节仍被追加到它之后。所以位置敏感的改动（增节 / 删节 / 换序 / 搬块）**第一手就用上面的重建法**，
别先用 `edit` 试一次再重建，那等于白白制造一个需要修的错误。

**推论**：凡"改动后的文件是否完整"这件事，答案必须来自**清单式 contains 校验**，不来自"记得没动过它"。

**备份自身也会丢东西（实测一次）**：备份那一步写成

```python
with open(bak, "w") as f:              # 先 open("w")：旧备份在这一刻已经被截断
    if not os.path.exists(bak):        # 这时判断必然是 False，什么都没写回
        f.write(old)
```

`open(..., "w")` **一执行就截断**已存在的文件，紧跟其后的存在性判断必然是 False——
「保留最早的备份」实际执行成了「删掉最早的备份」。曾把一个 5000 字节的 `.bak` 清成 0 字节
（真文件没坏，坏的是回滚点）。

**做法（祈使句）**：

1. **判断在前**：先 `if not os.path.exists(bak):`，再 `open(bak, "w")`；
2. 更稳的是**独占模式** `open(bak, "x")`——已存在就抛异常，绝不误伤；
3. 写完立刻断言 `os.path.getsize(bak) > 0`；
4. 收尾时**把所有 `.bak` 的大小打一遍**（靠这一步发现过 0 字节）。
   看到 0 字节先当成"是自己把它截断了"，去重建；别当成"本来就没备份"。

## 局部替换：锚点必须覆盖"所有要删掉的连续行"

**适用**：同一段连续文本内的局部替换（改代码块里的一行、改表里的一格）。范围比上一节更小，反而更容易放松警惕。

**反例（实测）**：把一份题解 md 里某题代码块的 `scanf("%d", &n);` 改成 `cin >> n;`。
锚点只取了被替换行的**下一行**（`cin >> s0 >> s1;`），新串里又重复写了一遍本该保留的 `string s0, s1;`——
于是锚点**之外**的旧 `scanf` 行与旧声明原样留下，`string s0, s1;` 出现两次，
编译直接报 `redeclaration of 'std::string s0'`。**而编辑工具当时返回的是"成功"，一声不吭。**

根因：`edit` 是"替换一段"语义，**锚点之外一个字都不会动**。以为"改了那一行"，实际改的是它旁边那一行。

**做法（祈使句）**：

1. 动手前先列出**这次要删掉的每一行**；锚点从第一行要删的取到最后一行要删的，**不要落在被替换内容的下一行**。
2. **保留行放在锚点之外**，新串里不要重复写——重复写就会多出一行。
3. 改完立刻做一次**能暴露"残留 / 重复"的检查**：代码块就提取出来重编译（重复声明当场报错），纯文本就 `contains` 计数（同一片段出现两次算失败）。
4. **"改成功"不等于"改对"**：返回成功只说明锚点匹配上了；结论要看改完之后的产物，不看工具的返回。

## 行尾约定（先探测，别假设）

**本库约定**：

| 文件类别 | 行尾 |
|---|---|
| 知识库文档 `knowledge/*.md` | **LF** |
| `.cmd` / `.bat` 批处理 | **CRLF（必须；且纯 ASCII）** |
| 交付用的 `.md`（含复制到 `desktop_copy_dir` 的那份副本） | **不统一，只能逐个探测**（同批交付里就混着 CRLF 与 LF） |
| C++ 源码 `.cpp` | **LF** |

**行尾按文件类型不同，不是"一台机器一个约定"**。
改任何文件前**先探测那一个文件**，别按上一个文件的习惯套——曾因为按 CRLF 拼锚点去改一个 LF 的 `.cpp`，白跑一轮。

**反例**：给本文件插入新章节时，脚本凭习惯把锚点转成 CRLF，而本文件是 LF → `Contains` 两次未命中，白跑两轮。
根因是**给原文加了一个它没有的假设**。

**做法（祈使句）**：改文件前**先探测行尾再拼串**——

```powershell
$t = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
$crlf   = ([regex]::Matches($t, "`r`n")).Count
$loneLf = ([regex]::Matches($t, "(?<!`r)`n")).Count   # 纯 LF 文件
```

纯 LF 文件用 `` "`n" `` 拼锚点与新内容，**不要转 CRLF**；改动后保持一致，校验项里加一条「CRLF 数与单独 LF 数不混合」。
